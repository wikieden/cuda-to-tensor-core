本章缩写：PTX = Parallel Thread Execution（并行 / 线程 / 执行，NVIDIA 的虚拟指令集）· ISA = Instruction Set Architecture（指令集架构）· SASS = Streaming ASSembler（真实机器码）· cubin = CUDA binary（某一代 GPU 的二进制）· fatbin = fat binary（"胖"二进制，装多份 cubin / PTX）· JIT = Just-In-Time（即时编译）· NVRTC = NVIDIA Runtime Compilation（运行时编译库）· sm_XX / compute_XX（真实架构 / 虚拟架构版本号）

讲解

第一步：两层指令集——PTX 与 SASS（2026-11-14）

PG §1.3.3：PTX 是一个虚拟指令集，"a high-level assembly language for NVIDIA GPUs"，在真实硬件指令之上提供一层抽象。

PTX SASS
是什么 虚拟汇编，跨代相对稳定 某一代 GPU 真正执行的机器码
版本 compute_80、compute_90a…… sm_80、sm_90a、sm_100a……
谁生成 nvcc、Triton、Rust 编译器等前端 ptxas 把 PTX 编成 SASS；驱动 JIT 也能编
看它为了什么 看写了什么指令（mma、cp.async.bulk.tensor） 看真正生成了什么（HMMA、LDG.E.128、有没有 spill）

类比： PTX 像菜谱，SASS 像某个厨房按自己的灶具改写后的操作卡。同一份菜谱，不同厨房（不同代 GPU）各自改写。

PG 还点出了一个重要意义：别的语言和 DSL 只要能生成 PTX，就能跑在 NVIDIA GPU 上——Triton、cuda-oxide（Rust）、Julia 都是这么做的。

第二步：nvcc 做了什么（2026-11-14）

my.cu ──nvcc──┬── host 代码 ──→ 普通 C++ 编译器 ──→ CPU 机器码
              └── device 代码 ──→ PTX ──ptxas──→ cubin（SASS）
                                         └────────┬───────┘
                                              fatbin（可装多份）
                                  两者链接进同一个可执行文件 / .so

PG §1.3.4：可执行文件里的 GPU 代码放在 fatbin 容器里，fatbin 可以同时装多个架构的 cubin 和 PTX；运行时，驱动从里面挑最适合当前 GPU 的那份。

# 同时生成 sm_80、sm_90a 的 cubin，再附一份 compute_90 的 PTX 留给未来
nvcc -gencode arch=compute_80,code=sm_80 \
     -gencode arch=compute_90a,code=sm_90a \
     -gencode arch=compute_90,code=compute_90 my.cu

看中间产物：nvcc -ptx my.cu（得到 PTX）、cuobjdump -sass a.out（看 SASS）；不装工具链时用 Godbolt 的在线 nvcc（04 调研 §1.6，Mac 上唯一的办法）。

第三步：兼容性规则（2026-11-14）

PG §1.3.4.1–1.3.4.3 的规则，记三条：

  1. cubin 只能往同一大版本的更高小版本兼容：为 8.6 编的 cubin 能在 8.6、8.9 上跑，不能在 8.0 上跑（小版本更低），也不能在 9.0 上跑（大版本不同）；
  2. PTX 能向前兼容：带了 compute_80 的 PTX，在任何 CC ≥ 8.0 的 GPU 上都能被驱动 JIT 编译——包括编译时还不存在的新卡。代价是首次加载要编译（结果缓存在 compute cache 里，驱动升级后自动失效重编）；
  3. 带 a 后缀的架构（sm_90a、sm_100a）不向前兼容：wgmma、setmaxnreg（第 18 章）、tcgen05（第 20 章）这些架构专属指令只在对应的 a 目标上可用，编出来的东西换一代就不能跑（〔旧知〕，与第 20 章"Blackwell 不认 wgmma"一致）。

实际后果：PyTorch、vLLM 这类库发布时要为一串 sm_XX 各编一份 cubin，再附一份最新 PTX；用了 Hopper / Blackwell 专属指令的 kernel 要按架构分别编译、运行时分别分派。

第四步：运行时编译——NVRTC（2026-11-14）

PG §1.3.4.3 最后一段：除了离线用 nvcc，还可以用 NVRTC 在程序运行时把 CUDA C++ 源码字符串编译成 PTX，再用 driver API 加载、启动。

什么时候需要：

  • kernel 的参数（tile 大小、数据类型）运行时才知道，想为每种组合生成专门的代码——DeepGEMM 就是运行时 JIT 编译 GEMM kernel 的（04 调研 §3.3）；
  • 宿主程序不是 C++（Python、Rust），又不想依赖 nvcc 构建流程——CuPy 的 RawKernel、cudarc 的 NVRTC 支持都是这条路；
  • Triton 也是运行时 JIT：第一次调用时把 Python 写的 kernel 编成 PTX → cubin，缓存起来。

第五步：Rust host + C++ kernel（2026-11-14）

03 Rust vs C++ §5 的选型结论：生产默认是"CUDA C++ kernel + cudarc（Rust host）"。原因：C++ 有 CUTLASS / CuTe 和完整工具链；Rust 在 host 端负责内存安全、并发和服务逻辑。

两种组合方式：

方式 做法 优缺点
预编译 构建时用 nvcc 把 .cu 编成 PTX / cubin，Rust 用 cudarc 加载 .ptx 文件或嵌进二进制的字节 启动快；构建要装 CUDA 工具链
运行时编译 Rust 读 .cu 源码字符串，cudarc 调 NVRTC 编译后加载 构建简单、可按参数特化；首次启动慢

study-plan 的 M10 就是这个模板：cudarc 加载 M3 写的 .cu，NVRTC 编译 + launch + 对拍 CPU。candle 的 candle-kernels/ 是现成的范例（预编译 PTX 嵌进 Rust crate）。

Rust 也能直接写 kernel（cuda-oxide、cutile-rs、CubeCL，01 Rust 生态），但截至 2026-10 的核对：H100 的 wgmma 支持不全、用不了 C++ 模板库（03 §3）。

第六步：发布 kernel——Hugging Face Kernels Hub（2026-11-14）

自己写的 kernel 怎么给别人用？04 调研 §3.4：Hugging Face 的 kernels 库——

  • 使用方：get_kernel("kernels-community/activation")，从 Hub 下载为当前 PyTorch × CUDA 组合预编译好的 kernel，直接调用；
  • 发布方：用 Nix 的 kernel-builder 为所有支持的 PyTorch / CUDA 版本组合各编一份（正是第三步说的"一串 sm_XX 都要编"），build-and-upload 上传，有现成的 GitHub Action。

这解决了 CUDA kernel 分发最头疼的问题：用户的 PyTorch 版本、CUDA 版本、GPU 架构五花八门。

数学原理

  • cubin 可加载条件：cubin 目标 sm_XY，GPU 为 X'.Y'，可加载当且仅当 \(X' = X\) 且 \(Y' \ge Y\)（PG §1.3.4.1）。
  • PTX 可 JIT 条件：PTX 目标 compute_XY，GPU 计算能力 \(\ge X.Y\)（非 a 目标）。

关键几行：

kind, major, minor, a = parse(target)       # "sm_90a" → ("sm", 9, 0, True)
if a:                                        # 架构专属：只认同一个架构
    return ... if (major, minor) == cc else None
if kind == "sm":                             # cubin：同一大版本、小版本不低于它
    return "cubin" if cc[0] == major and cc[1] >= minor else None
return "JIT" if cc >= (major, minor) else None   # PTX：任何更新的卡都能 JIT

代码里才看得到的 3 件事：

  1. Python 的元组比较是逐项比：(10, 0) >= (8, 0) 为 True，正好就是"CC 不低于"的意思。
  2. fatbin 里 cubin 优先于 PTX：能直接跑的机器码不用现场编译；都不能直接跑时才 JIT（首次加载慢，结果会缓存）。
  3. 讲义那条 nvcc 命令只给 sm_90a 编了 cubin、没带 compute_90a 的 PTX：所以 10.0 的卡用的是普通 compute_90 那份 PTX——里面不能有 wgmma 这类 9.0a 专属指令。

  • 把 fatbin 换成只有一份 compute_80 PTX，看 8.0、9.0、10.0 的卡各挑什么、哪些要 JIT。
