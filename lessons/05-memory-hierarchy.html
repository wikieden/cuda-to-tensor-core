本章缩写：HBM = High Bandwidth Memory（高带宽 / 显存，堆叠在 GPU 旁边的 DRAM）· DRAM = Dynamic Random-Access Memory（动态 / 随机访问 / 存储器）· SRAM = Static RAM（静态随机存储器，片上缓存用的）· GMEM / SMEM / RMEM = Global / Shared / Register MEMory（全局内存 / 共享内存 / 寄存器）· DSMEM = Distributed Shared MEMory（分布式 / 共享内存）· L1 / L2 = Level 1 / Level 2 cache（一级 / 二级缓存）

讲解

第一步：为什么要分层——快的贵且小（2026-11-14）

Gordić 的解释（第 39 行）：片上 SRAM 快，但每个存储单元面积大；DRAM 密度高，但慢。所以芯片设计只能妥协：离计算单元最近放一点点最快的，往外一层层放更大、更慢的。

类比：厨师做菜。

层 厨房里对应 谁管
寄存器 RMEM 厨师手里拿着的食材 编译器
shared memory SMEM 灶台边的小台面，同一个灶的几个厨师（同一 block）共用 你
L1 cache 灶台边的小冰箱，自动放最近用过的 硬件
L2 cache 后厨的大冷库，所有灶（所有 SM）共用 硬件
显存 HBM（global memory） 城外仓库，什么都有，但一趟要很久 你（分配、拷贝、怎么读）

第二步：H100 每一层的数字（2026-11-14）

层 容量（H100 SXM） 带宽 / 延迟量级 作用域 来源
寄存器 每 SM 64K 个 32 位寄存器 = 256 KB；每线程最多 255 个 每周期就能用，延迟最低 单个线程 Hopper guide §4.1.1
shared memory + L1 每 SM 共 256 KB 片上存储，其中 shared 最多 228 KB（单个 block 最多 227 KB） 延迟约几十个周期 〔旧知〕 一个 block（cluster 内可跨 block，叫 DSMEM） Hopper guide §4.1.1、§4.2.4
L2 50 MB，全 GPU 共享 延迟约两百周期 〔旧知〕 所有 SM Hopper guide §4.2.2
HBM3 80 GB 约 3.35 TB/s（Hopper guide 写 up to 3 TB/s）；延迟约几百周期 〔旧知〕 所有线程 + host 拷贝 Hopper guide §4.2.1

有两个反直觉的地方：

  1. 寄存器总量和 shared + L1 一样大（Gordić 第 50 行）：每个 SM 256 KB 寄存器。CPU 每个核心才几 KB 寄存器。GPU 把大量面积给了寄存器，因为要同时养活几十个 warp（第 2 章：warp 切换不花代价，前提是每个 warp 的寄存器一直放在片上）。
  2. 132 个 SM 的 shared memory 加起来约 30 MB，和 L2 是同一个量级。所以"把数据放进 shared memory 反复用"能装下的东西并不少。

延迟数字没有在本地文档里找到官方表，上表只给量级（〔旧知〕）。记住规律就够了：每往外走一层，延迟大约高一个数量级，带宽低一个数量级，容量大一到两个数量级（Gordić 第 53 行）。

第三步：kernel 里的变量放在哪（2026-11-14）

PG §2.3.3 逐个讲了每种内存。对照代码最清楚：

__constant__ float coef[16];                 // 常量内存：只读、所有线程看同一份，有专门的缓存

__global__ void k(float* g, int n) {         // g 指向 global memory（显存）
    __shared__ float tile[256];              // shared memory：整个 block 一份
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // i：寄存器
    float acc = 0.0f;                        // acc：寄存器
    float buf[4];                            // 小数组、下标是常量 → 通常放寄存器
    float big[256];                          // 大数组或下标运行时才知道 → local memory（其实在显存里！）
    tile[threadIdx.x] = g[i];                // 显存 → shared
    __syncthreads();
    acc += tile[(threadIdx.x + 1) % 256] * coef[0];
    g[i] = acc;                              // 寄存器 → 显存
}

最大的坑：local memory 不在本地。 PG §2.3.3.4 原话："The 'local' label refers to its logical scope, not its physical location"——"local"说的是只有这个线程能看见，物理位置却在显存里，延迟和带宽都和 global memory 一样。编译器在三种情况下会把变量放到 local memory：

  1. 数组的下标编译时确定不了（如 buf[k]，k 是运行时变量）；
  2. 结构体或数组太大，寄存器放不下；
  3. 寄存器用超了，溢出（spill）。

用 nvcc -Xptxas -v（或 --resource-usage）编译能看到每个 kernel 用了多少寄存器、有没有 spill。

第四步：谁管谁——优化就是"把数据往上搬，搬一次多用几次"（2026-11-14）

内存 程序员能控制什么
寄存器 间接：少用大数组、循环展开要适度、__launch_bounds__ 限制（第 8 章）
shared memory 完全手动：声明、谁写谁读、__syncthreads() 同步
L1 / L2 基本自动；可以给提示（如 L2 持久化窗口，PG §4.14）
global memory 分配和拷贝；访问模式决定效率（下一章的合并访存）

后面大半本书的优化都是同一个思路：数据从显存读进来一次，在 shared memory / 寄存器里被多个线程、多次计算复用。矩阵乘法（第 13–14 章）、归约（第 10 章）、FlashAttention（第 22 章）全是这个套路。

数学原理

  • 复用率决定该放哪层：一个数据被读 \(r\) 次。全放显存要读 \(r\) 次显存；先搬进 shared 再读，只读 1 次显存 + \(r\) 次 shared。\(r\) 越大收益越大；\(r=1\)（比如向量加法）时搬进 shared 毫无意义。
  • 寄存器约束：每线程寄存器数 \(R\)、block 线程数 \(T\)，要求 \(R \cdot T \le 65536\)（每 SM 的寄存器总数），否则 kernel 启动失败（PG §1.2.3.3 原文）。
