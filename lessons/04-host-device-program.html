讲解

第一步：两块内存，中间一条窄路（2026-11-14）

CPU 和 GPU 各有各的内存：

  • host 内存：插在主板上的内存条，CPU 直接读写；
  • device 内存：GPU 显卡上的显存（HBM / GDDR），kernel 直接读写。

两者之间靠 PCIe（或 NVLink-C2C 等）连接。这条路比两边的内存都窄得多：PCIe 5.0 x16 单方向约 64 GB/s，而 H100 显存带宽约 3.35 TB/s，差了 50 倍（〔旧知〕规格书数字）。

类比：工厂和仓库。 CPU 是总部办公室，GPU 是城外的大工厂，显存是工厂自己的仓库。原料要先用卡车从总部运到工厂仓库（H2D），工厂加工完再把成品运回来（D2H）。卡车路很窄，所以：原料尽量一次运过去、在工厂里多加工几道，别来回跑。

（PG §2.1.3.1 还有一条省事的路：Unified Memory，cudaMallocManaged 分配一块两边都能用的内存，系统自动搬。入门方便，但想控制性能时要用下面的显式写法。）

第二步：标准五步（2026-11-14）

PG §2.1.3.2 的完整例子，压缩成五步：

// ① 分配：host 用 cudaMallocHost（锁页内存，拷贝更快），device 用 cudaMalloc
float *A, *devA, *devB, *devC;
cudaMallocHost(&A, n * sizeof(float));
cudaMalloc(&devA, n * sizeof(float));
// ... devB、devC 同理

// ② 拷进去：H2D
cudaMemcpy(devA, A, n * sizeof(float), cudaMemcpyDefault);

// ③ 启动 kernel（第 1 章的配方）
int threads = 256;
int blocks  = cuda::ceil_div(n, threads);      // 就是 (n + 255) / 256
vecAdd<<<blocks, threads>>>(devA, devB, devC, n);

// ④ 等 GPU 做完，再拷回来：D2H
cudaDeviceSynchronize();
cudaMemcpy(C, devC, n * sizeof(float), cudaMemcpyDefault);

// ⑤ 释放
cudaFree(devA); cudaFreeHost(A);

几个要点：

  • devA 是显存地址，CPU 不能直接 devA[0] 去读，只能通过 cudaMemcpy 搬回来再读。kernel 里也不能读 host 的普通指针。
  • cudaMemcpyDefault 让运行时根据指针自己判断方向（统一虚拟地址下可用）；老代码写 cudaMemcpyHostToDevice / cudaMemcpyDeviceToHost，意思一样。
  • cudaMallocHost 分配的是锁页内存（pinned memory）：操作系统保证这块内存不会被换出到磁盘，GPU 可以直接用 DMA 搬，比普通 malloc 的内存快，也是异步拷贝的前提（Best Practices §10.1.1；第 26 章 streams 会用到）。

第三步：kernel 启动是"下单"，不是"等做完"（2026-11-14）

PG §2.1.4：kernel 启动对 CPU 来说是异步的。vecAdd<<<...>>>(...) 这一行只是把任务放进 GPU 的队列，CPU 立刻往下执行，不等 GPU 算完。

类比：外卖下单。 你点完单（启动 kernel）可以继续干别的；想吃的时候（要用结果时）得等外卖到了（同步）。

所以：

  • cudaDeviceSynchronize()：CPU 停下来，等 GPU 上之前所有的活都做完；
  • cudaMemcpy（不带 Async 的版本）本身会等前面的 kernel 做完再拷，所以上面第 ④ 步严格来说不写 cudaDeviceSynchronize() 也能得到正确结果；但 PG 的例子里显式写了，读代码的人一眼能看出"这里要等"；
  • 用 CPU 计时器测 kernel 时间，一定要先同步，否则测到的只是"下单花了多久"（几微秒），不是 kernel 真正的耗时。第 9 章讲正确计时。

第四步：查错——错误会"晚到"（2026-11-14）

PG §2.1.7：每个 CUDA API 都返回 cudaError_t，成功是 cudaSuccess。常用宏：

#define CUDA_CHECK(x) do { cudaError_t e = (x); if (e != cudaSuccess) {      \
    fprintf(stderr, "%s:%d: %s\n", __FILE__, __LINE__, cudaGetErrorString(e)); \
    exit(1); } } while (0)

CUDA_CHECK(cudaMalloc(&devA, bytes));

两个坑：

  1. <<< >>> 启动不返回错误码。 启动后要立刻调 cudaGetLastError() 查一次。PG 原话：这时查到 cudaSuccess 不代表 kernel 跑成功了，甚至不代表它开始跑了，只说明启动参数没问题（比如 block 超过 1024 个线程就会在这里报错）。
  2. kernel 运行中的错误（如越界访问）是异步报告的，会在之后某个同步点的返回值里冒出来，看起来像是"下一个无关的 API 出错了"。调试时可以在每个 kernel 后加 cudaDeviceSynchronize() 再查错，把错误定位到具体 kernel。
vecAdd<<<blocks, threads>>>(devA, devB, devC, n);
CUDA_CHECK(cudaGetLastError());        // 查启动参数错误
CUDA_CHECK(cudaDeviceSynchronize());   // 调试时：查 kernel 运行中的错误

越界这类错误更好的查法是 compute-sanitizer（compute-sanitizer ./my_prog），它会直接告诉你哪个 kernel、哪个线程、哪个地址越界（04 调研 §1.6）。

第五步：算一笔账——小 kernel 不值得搬（2026-11-14）

向量加法，n = 1 亿个 float（400 MB 一个数组）：

步骤 搬多少 带宽 耗时
H2D 拷 A、B 800 MB PCIe 5.0 约 64 GB/s ≈ 12.5 ms
kernel：读 A、B，写 C 1200 MB 显存约 3.35 TB/s ≈ 0.36 ms
D2H 拷 C 400 MB 约 64 GB/s ≈ 6.3 ms

kernel 本身不到 0.4 ms，搬运要将近 19 ms。只为做一次加法把数据搬上 GPU，得不偿失。 真实的 AI 程序里，模型权重和激活一直留在显存里，几百个 kernel 接力处理，只有输入和最终结果才走 PCIe——这就是第一步说的"别来回跑"。

口诀

五步走：分配、拷进、启动、同步、拷回（最后释放）；

数学原理

  • 搬运时间 ≈ 字节数 ÷ 带宽 + 固定开销（每次 cudaMemcpy 约几微秒）。小块拷贝时固定开销占主导，所以要合并成大块拷。
  • 值不值得上 GPU：粗估 \(t_{\text{GPU}} = t_{\text{H2D}} + t_{\text{kernel}} + t_{\text{D2H}}\)，和 CPU 耗时比。计算量相对数据量越大（算术强度越高，第 9 章），越值得。

代码里才看得到的 3 件事：

  1. FakeGPU.mem 是一个字典，CPU 端只能通过 memcpy_* 拿数据：对应讲义说的"devA 是显存地址，CPU 不能直接 devA[0]"。
  2. memcpy_d2h 里先调了 synchronize()：这就是"不带 Async 的 cudaMemcpy 会等前面的 kernel 做完"。
  3. D2H 算出来是 6.25 ms：讲义表里写 ≈ 6.3 ms 是四舍五入到一位小数，测试按 6.25 核对。
