讲解

第一步：归约是什么、什么运算能并行归约（2026-11-14）

归约（reduction）：用一个二元运算 ∘ 把一串数并成一个数，\(v = u_0 \circ u_1 \circ \cdots \circ u_{N-1}\)。求和、求积、最大值、最小值都是。

Oxford lec4 第 9 页：能并行归约的运算要满足

  • 结合律：\((a \circ b) \circ c = a \circ (b \circ c)\)——这样才能随便分组；
  • 最好也满足交换律：\(a \circ b = b \circ a\)——这样才能随便换顺序。

一个要小心的地方（Oxford 同页）：浮点加法严格来说不满足结合律，\((a + b) + c\) 和 \(a + (b + c)\) 可能差在最后几位。所以 GPU 上并行求和的结果和 CPU 顺序求和不会一模一样，对拍要用容差（04 调研 §4.3）。

第二步：树形归约——像淘汰赛（2026-11-14）

CPU 顺序加 N 个数要 N − 1 步。GPU 上换成淘汰赛：

  • 第 1 轮：8 个数两两配对，4 个线程各加一对 → 剩 4 个；
  • 第 2 轮：2 个线程 → 剩 2 个；
  • 第 3 轮：1 个线程 → 剩 1 个。

总加法次数还是 N − 1，但轮数只有 \(\log_2 N\)。256 个数只要 8 轮。

Oxford lec4 第 15 页的 block 内归约代码（"前一半加后一半"）：

__global__ void sum(float* d_sum, float* d_data) {
    extern __shared__ float temp[];
    int tid = threadIdx.x;
    temp[tid] = d_data[tid + blockIdx.x * blockDim.x];   // 每个线程搬一个数进 shared
    for (int d = blockDim.x / 2; d > 0; d = d / 2) {
        __syncthreads();                                  // 上一轮全部写完再读
        if (tid < d) temp[tid] += temp[tid + d];          // 前 d 个线程：自己 + 后半段对应位置
    }
    if (tid == 0) d_sum[blockIdx.x] = temp[0];            // 每个 block 留一个部分和
}

数字演示（blockDim = 8，数据 [3, 1, 4, 1, 5, 9, 2, 6]）：

轮 d 干活的线程 temp 变成

1 4 0–3：temp[t] += temp[t+4] 8 10 6 7 5 9 2 6
2 2 0–1：temp[t] += temp[t+2] 14 17 6 7 …

3 + 1 + 4 + 1 + 5 + 9 + 2 + 6 = 31 ✓。

第三步：为什么是"前一半加后一半"（2026-11-14）

另一种看起来也对的写法是相邻两两相加（interleaved addressing）：

for (int s = 1; s < blockDim.x; s *= 2) {
    __syncthreads();
    if (tid % (2 * s) == 0) temp[tid] += temp[tid + s];
}

结果一样，但慢。两个原因，正好是第 3、7 章的内容：

相邻两两相加 前一半加后一半
第 1 轮干活的线程 0、2、4、6…（隔一个） 0、1、2、3…（连续的前一半）
warp 分岔（第 3 章） 每个 warp 都分岔：一半 lane 干活、一半屏蔽，后几轮更稀疏 前几轮整个 warp 要么全干、要么全不干；只有剩不到 32 个线程时才分岔
bank conflict（第 7 章） 第 2 轮线程 t 访问 temp[4k]，跨步 4 → 4 路冲突，越往后越严重 连续线程访问连续地址，无冲突
% 运算 每轮都要算，取模很慢 只要比较

Mark Harris 的经典讲稿里，这一改动在 G80 上把带宽提升约 2 倍（〔旧知〕）。本仓库 cubecl-lab M1 的注释里也留了这道思考题。

第四步：block 之间怎么合（2026-11-14）

每个 block 算出一个部分和，还要把它们加起来。第 2 章说过 block 之间不能互相等，所以有两条路（Oxford lec4 第 17–18 页）：

  1. 两次 kernel：第一个 kernel 每个 block 写一个部分和到 d_sum[blockIdx.x]；第二个 kernel（或 CPU）再把这几百个部分和归约掉。kernel 之间天然有先后。
  2. 原子加：每个 block 的 0 号线程直接 atomicAdd(&total, temp[0])。硬件保证并发的原子加不会互相覆盖，只要一个 kernel。下一章细讲。

第五步：每个线程先多加几个——grid-stride loop（2026-11-14）

上面的写法一个线程只搬一个数，数据有 1 亿个就要 1 亿个线程、39 万个 block，大部分时间花在"开线程、进 shared、同步"上，真正的加法很少。

更好的做法：固定开不多的 block（比如 SM 数的几倍），每个线程先在寄存器里顺序加很多个数，再进树形归约：

float acc = 0.0f;
for (int i = blockIdx.x * blockDim.x + threadIdx.x; i < n; i += gridDim.x * blockDim.x)
    acc += data[i];            // 步长 = 整个 grid 的线程数，每次循环整个 grid 合并地读一段
temp[tid] = acc;
// ……接树形归约

这叫 grid-stride loop：每一圈，整个 grid 的线程一起读连续的一大段（合并访存，第 6 章），一圈圈往后推。好处：

  • block 数和数据量无关，不会碰到 grid 大小上限（cubecl-lab 的 M1c 就是为了解决 WebGPU 每维 65535 个 workgroup 的限制）；
  • 大部分加法在寄存器里完成，shared memory 和同步的开销被摊薄；
  • 归约是典型的 memory-bound 运算（每读 4 字节只做 1 次加法），目标是打满显存带宽（第 9 章）。

数学原理

  • 工作量与步数：树形归约总运算次数 \(N - 1\)（和顺序算法一样，叫 work-efficient），并行步数 \(\lceil \log_2 N \rceil\)。
  • 浮点误差：顺序求和的误差上界随 \(N\) 线性增长，树形求和随 \(\log N\) 增长——并行归约通常更准，只是和顺序结果不逐位相同。
  • grid-stride 的覆盖：线程全局号 \(g\)、总线程数 \(P\)，访问 \(g, g+P, g+2P, \dots\)；所有线程合起来恰好覆盖 \(0..n-1\) 一次。

关键几行：

d = len(temp) // 2
while d > 0:                              # 每一轮之前有一道 __syncthreads()
    for t in range(d):                    # 前 d 个线程同时做
        temp[t] += temp[t + d]
    d //= 2

acc[tid] = data[tid::total].sum()         # grid-stride：每次跳过整个 grid 的线程数

代码里才看得到的 3 件事：

  1. Python 的 for 循环是一个一个做的：同一轮里"前 d 个线程同时做"在这里写成循环；能这样写是因为同一轮里每个线程读写的位置互不重叠（读 t + d、写 t）。
  2. data[tid::total] 就是 grid-stride 的下标序列：从自己的全局编号开始，每次加 grid 的总线程数。
  3. 100 万个 float32 两种加法顺序结果不同：np.cumsum 是一个一个顺序加，np.sum 内部分组两两加，最后几位不一样——GPU 和 CPU 对拍要用容差（第 27 章）。
