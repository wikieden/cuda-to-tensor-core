本章缩写：GMEM = Global MEMory（全局内存，即显存）· LDG = LoaD Global（从全局内存读的 SASS 指令）· SASS = Streaming ASSembler（GPU 真正执行的机器码）

讲解

第一步：显存按 32 字节一块一块地给（2026-11-14）

PG §2.3.4.1 第一句："Global memory is accessed via 32-byte memory transactions."——显存按 32 字节一块（sector，扇区） 来读写。线程只要 4 字节的一个 float，硬件也得搬整整 32 字节回来。

类比：快递按箱发货。 仓库只按箱发货，一箱 32 字节（8 个 float）。你要 1 个，也得运来一整箱。

一个 warp 的 32 个线程同时发出读请求，硬件把这 32 个地址合并（coalesce）：落在同一箱里的请求只运一箱。所以关键问题是：32 个地址落在几箱里？

第二步：三种情况算一算（2026-11-14）

每个线程读一个 4 字节 float，warp 一共需要 32 × 4 = 128 字节有用数据。

访问方式 代码 落在几箱 搬运量 利用率
① 相邻线程读相邻地址 a[i] 128 / 32 = 4 箱 128 B 100%
② 错位：整体平移 1 个 float a[i + 1] 5 箱（首尾各跨一箱） 160 B 80%
③ 跨步 2 a[2 * i] 8 箱 256 B 50%
④ 跨步 ≥ 8（间隔 ≥ 32 字节） a[8 * i]、a[i * n] 32 箱（每个线程一箱） 1024 B 12.5%

①④ 是 PG 原文的两个例子："perfectly coalesced" 4 次传输、100% 利用；最坏情况 32 × 32 = 1024 字节，利用率 128 / 1024 = 12.5%。② 是 Best Practices §10.2.1.2 的例子：错位让 4 箱变 5 箱。

跨步 s 的一般公式（s 个 float 为间隔，s ≤ 8）：32 个线程覆盖 \(32s\) 个 float = \(128s\) 字节，即 \(4s\) 箱；利用率 \(= 1/s\)。s ≥ 8 之后每个线程独占一箱，利用率停在 1/8。

两个细节：

  • 顺序打乱没关系（Best Practices §10.2.1.1）：只要 32 个地址落在同样那 4 箱里，线程 0 读第 5 个、线程 5 读第 0 个，也还是 4 箱。PG 原话："maximize the ratio of bytes used to bytes transferred"——比的是用到的字节 ÷ 搬来的字节。
  • 错位的实际损失比算出来小：Best Practices 在 V100 上实测，错位读的带宽是对齐时的约 9/10 而不是 4/5，因为相邻 warp 会用到邻居多搬来的那一箱（L2 / L1 命中）。跨步就没这么幸运了。cudaMalloc 返回的地址至少 256 字节对齐，所以只要下标从 0 开始、block 大小是 32 的倍数，就天然对齐。

第三步：二维数组——按行还是按列（2026-11-14）

C/C++ 的二维数组按行优先存：A[r][c] 在内存里的位置是 r * N + c，同一行的元素挨着放。

// 每个线程负责一个 (row, col)，threadIdx.x 是 warp 里变化最快的那个
int col = blockIdx.x * blockDim.x + threadIdx.x;
int row = blockIdx.y * blockDim.y + threadIdx.y;

out[row * N + col] = in[row * N + col];   // ✅ 相邻线程 col 相邻 → 地址相邻 → 合并
out[col * N + row] = in[col * N + row];   // ❌ 相邻线程地址相差 N 个 float → 每线程一箱

记住一句：让 threadIdx.x 对应内存里变化最快的那个下标（最后一维）。

矩阵转置是个躲不开的难题（PG §2.3.4.1.1）：out[c][r] = in[r][c]，读按行合并了，写就必然按列；反过来也一样。解决办法是先按行读进 shared memory，在 shared memory 里转置，再按行写出去（PG §2.3.4.2.1）——这需要下一章的 shared memory，还会遇到 bank conflict。

第四步：一次读更多——向量化（2026-11-14）

每个线程一次读 4 字节，一个 warp 一条指令只拿 128 字节。改成每个线程一次读一个 float4（16 字节）：

float4 v = reinterpret_cast<const float4*>(a)[i];   // 要求地址 16 字节对齐

一个 warp 一条指令拿 512 字节（16 箱，仍然 100% 利用），指令数变成 1/4。编译出来的 SASS 是 LDG.E.128（128 位读）。对于 memory-bound 的 kernel（逐元素运算、归约、norm），这是最便宜的提速手段之一（04 调研 §5.1；Boehm GEMM kernel 6 也用了它）。

数学原理

  • 箱数：warp 的 32 个地址 \(\{a_k\}\)（字节），箱数 = 不同的 \(\lfloor a_k / 32 \rfloor\) 的个数。
  • 跨步 s（以 4 字节为单位）：\(s \le 8\) 时箱数 \(= 4s\)（对齐时），利用率 \(= 1/s\)；\(s \ge 8\) 时箱数 = 32，利用率 = 1/8。
  • 错位偏移 o 个 float（0 < o < 8）：32 个连续 float 跨 \(\lceil (o + 32)/8 \rceil = 5\) 箱。

关键几行：

SECTOR = 32
def sectors(byte_addrs):                   # 32 个地址落在几箱
    return len(np.unique(byte_addrs // SECTOR))

t = np.arange(32)                          # 一个 warp 的 32 个线程
addrs = (t * stride + offset) * 4          # 线程 t 读 a[t * stride + offset]（float）
utilization = 32 * 4 / (sectors(addrs) * 32)   # 用到的字节 ÷ 搬来的字节

代码里才看得到的 3 件事：

  1. 地址假设从 0 开始：warp_addrs 默认数组起点对齐到 32 字节（cudaMalloc 至少 256 字节对齐），所以 a[i] 正好 4 箱；offset = 1 就是错位的情形。
  2. 这里只数箱，不模拟缓存：讲义说错位读在 V100 上实测只损失约 1/10，因为邻居 warp 会命中 L1 / L2；代码按"每个 warp 单独搬"算，得到的是 4/5，是最坏情况。
  3. np.unique 天然忽略顺序：所以打乱 32 个地址箱数不变，和 Best Practices §10.2.1.1 说的一样。
