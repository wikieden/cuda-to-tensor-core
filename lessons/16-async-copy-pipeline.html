本章缩写：LDGSTS = LoaD Global, STore Shared（读全局、写共享，cp.async 对应的 SASS 指令）· CC = Compute Capability（计算能力）

讲解

第一步：同步 tile 循环的空转（2026-11-14）

第 13 章的循环：

for 每一段 K:
    ① 读显存 → 写 shared      （显存忙，计算单元闲）
    ② __syncthreads()
    ③ 用 shared 算             （计算单元忙，显存闲）
    ④ __syncthreads()

① 和 ③ 是串着的。设搬一块要 4 个单位时间、算一块要 4 个单位，8 段 K 就是 8 × (4 + 4) = 64 个单位。如果"搬第 k+1 块"和"算第 k 块"能同时做，就接近 4 + 8 × 4 = 36 个单位。

类比：流水线做饭。 不是"洗完一个菜、切完、炒完，再洗下一个"，而是"炒第 1 个菜的时候，第 2 个菜已经在洗了"。

第 8 章靠"多个 warp 轮流"来藏延迟；这一章是另一条路：同一个 warp 自己把"搬"和"算"错开。高性能 GEMM 的 occupancy 很低（第 14 章），恰恰更需要这一招。

第二步：老写法的两个问题（2026-11-14）

As[ty][tx] = A[...];      // 实际上是两步：LDG（显存 → 寄存器） + STS（寄存器 → shared）
  1. 会卡住线程：STS 要等 LDG 的数据到了才能执行，这个线程在这里停几百个周期；
  2. 绕道寄存器：数据先进寄存器再写 shared，白白占用寄存器和指令（Best Practices §10.2.3.4："avoids an intermediary register file access"）。

想"搬下一块"的同时"算这一块"，就得先把下一块的数据读进寄存器暂存——寄存器又不够（第 14 章的 GEMM 已经用了上百个）。

第三步：cp.async——下单直送台面，不经过手（2026-11-14）

Ampere（CC 8.0）加了 LDGSTS，PTX 叫 cp.async（PG §4.12.1）：

  • 一条指令直接从显存搬到 shared memory，不经过寄存器；
  • 异步：发出后线程立刻往下走，硬件在后台搬；
  • 每次搬 4 / 8 / 16 字节；16 字节时绕过 L1（L1 BYPASS），不污染缓存；最好 128 字节对齐；
  • 搬完了要靠完成机制告诉你：老的 commit_group / wait_group，或者 barrier / pipeline 对象。
// PTX 风格（CUTLASS / 手写 kernel 常用）
cp.async.cg.shared.global [smem_addr], [gmem_addr], 16;   // 发出一次 16 字节异步拷贝
cp.async.commit_group;                                     // 把之前发出的打成一组
cp.async.wait_group 1;                                     // 等到"最多还剩 1 组没完成"
__syncthreads();                                           // 别人搬的数据我也要看见

PG 的提醒：每个线程默认只等自己发出的拷贝，所以等完之后还要 __syncthreads()，别人搬的那部分才对你可见。

C++ 层面的封装是 cuda::memcpy_async + cuda::pipeline（PG §4.11、§4.12.1.2 的例子），CUTLASS 里叫 cp_async。

第四步：双缓冲与多级流水线（2026-11-14）

有了"发出就走"的拷贝，就可以开两份 shared buffer（双缓冲）：

预取：发出 第 0 块 → buf[0]
for k = 0 .. n-1:
    发出 第 k+1 块 → buf[(k+1) % 2]      // 异步，不等
    等 第 k 块 到齐（wait_group 1 + __syncthreads）
    用 buf[k % 2] 计算
    __syncthreads()                      // 大家算完，buf[k % 2] 才能被下下轮覆盖

推广到 S 级（S stages）：开 S 份 buffer，始终有 S − 1 块在路上。PG §4.12.1.2 的 prefetch_kernel<num_stages> 就是这个结构：shared_offset[s] = s * block.size()，用 (stage + 1) % num_stages 轮转。

为什么要多于 2 级？ 显存延迟很长（几百周期）而且不稳定，一块算完时下一块可能还没到。多几块在路上，等待的概率就小。代价是 shared memory 用量 × S。CUTLASS 的 Ampere GEMM 常用 3–5 级（〔旧知〕），具体由 shared memory 预算和 tile 大小决定。

数字演示（搬 4、算 2，单位时间；8 块）：

方式 总时间 说明
同步：搬完再算 8 × (4 + 2) = 48 串行
双缓冲 8 × 4 + 2 = 34 搬比算慢，瓶颈在搬：8 次搬运首尾相接，只多出最后一块的计算；计算被完全藏进搬运
3 级 34 搬是瓶颈时，多加级数也快不了——流水线最多把总时间压到 max(搬, 算) × n

反过来，算比搬慢（GEMM 的正常情况）时，流水线让显存搬运完全藏在计算后面，总时间 ≈ 算的时间。流水线不能让慢的那一步变快，只能把快的那一步藏起来。

第五步：同步原语的升级——barrier 的"相位"（2026-11-14）

__syncthreads() 是"全员停下等"。异步拷贝时代需要更细的同步："数据到了"和"大家用完了"是两件不同的事。PG §4.10 的异步 barrier（cuda::barrier）：

  • 初始化时设定"期望到达数"；
  • 线程调 arrive() 报到（不停下），拿到一个 token；
  • 需要时再调 wait(token) 等这一轮（phase，相位）完成；
  • 计数到零时，barrier 自动重置、进入下一相位（PG §4.10.2）。

"先报到、做点别的、再等"——让同步本身也可以和计算重叠。Hopper 的 mbarrier 在此基础上还能按字节数计数（"等 TMA 搬完 32 KB"），下一章细讲。

口诀

搬完再算两头闲，搬这块时算上块；
cp.async 下单直送台面：不经寄存器、发了就走，搬完只告诉自己，别人要看还得同步；
双缓冲两份台面轮着用，多级流水多几块在路上；
流水线只能藏起快的那一步，慢的那一步决定总时间；
barrier 有相位：先报到、做别的、再等。

数学原理

  • 流水线时间：\(n\) 块、每块搬 \(t_l\)、算 \(t_c\)。同步：\(n(t_l + t_c)\)。足够级数的流水线：\(\approx n \cdot \max(t_l, t_c) + \min(t_l, t_c)\)（慢的那一步首尾相接，再加上开头或结尾露在外面的一段快的）。加速比上限 \(\frac{t_l + t_c}{\max(t_l, t_c)} \le 2\)。
  • 需要几级：要藏住延迟 \(L\)，在路上的块数 \(\times\) 每块计算时间 \(\ge L\)，即 \(S - 1 \ge L / t_c\)（Little 定律的又一次应用，第 8 章）。

关键几行：

for i in range(n):
    start = loads[-1][1] if loads else 0            # 搬运一块接一块
    if i >= stages:
        start = max(start, computes[i - stages][1]) # 等第 i − S 块算完，buffer 才空
    loads.append((start, start + t_load))
    c0 = max(loads[i][1], computes[-1][1] if computes else 0)
    computes.append((c0, c0 + t_compute))           # 算要等这块搬完

代码里才看得到的 3 件事：

  1. stages = 1 就是同步写法：只有一份 buffer，搬第 i 块要等第 i − 1 块算完，搬和算完全串行。
  2. 模型里只有一条显存通道：搬运一块接一块，所以"搬是瓶颈"时多加 buffer 也快不了；真实 GPU 上多个 block 一起搬，但每个 block 的规律相同。
  3. Barrier.done(token) 看的是相位有没有翻过去：和 cuda::barrier::wait(token) 一样，token 记下的是 arrive 时的相位。
