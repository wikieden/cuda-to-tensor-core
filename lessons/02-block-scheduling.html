讲解

第一步：GPU 是一排车间，block 是一张张工单（2026-11-14）

GPU 芯片上有很多个 SM。H100 SXM 有 132 个，B200 有 148 个，入门级的 T4 有 40 个。每个 SM 是一个独立的"车间"：有自己的计算单元、寄存器和 shared memory。

启动 kernel 时，grid 里的每个 block 就是一张工单。硬件里的调度器（block scheduler）做的事很简单（PG §2.3.7）：

  1. 看哪个车间还有空位（寄存器、shared memory、线程数都够），就把一张工单派过去；
  2. 所有车间都满了，就等，等某个车间做完一张工单再派下一张；
  3. 直到所有工单派完、做完。

PG 原文强调两点：派到哪个 SM、按什么顺序派，程序既不能控制也不能查询；而且 "no ordering guarantees are made by the scheduler"（调度器不保证任何顺序）。

一个 block 一旦派给某个 SM，就在那个 SM 上一直跑到结束（PG §1.2.2.1："run to completion on that SM"）。所以同一个 block 的线程共享这个 SM 的 shared memory、能用 __syncthreads() 互相等——这是第 1 章说"block 是能互相配合的一组线程"的硬件原因。

第二步：为什么不同 block 不能互相等（2026-11-14）

假设 block 7 要等 block 900 先算出一个数。如果 GPU 上同时只能放 264 个 block（132 个 SM × 每个 2 个），block 900 根本还没被派出去；而 block 7 占着车间在死等，它不走，就腾不出位置给 block 900——死锁。

所以 PG 立了一条规矩（§1.2.2.1）：

程序必须允许 block 以任意顺序、并行或串行地执行。

也就是说：同一个 grid 里，一个线程不能依赖另一个 block 的结果，也不能和另一个 block 的线程同步。

这条规矩换来的好处是可扩展性：同一个程序，在 40 个 SM 的 T4 上一次跑 40 份，在 148 个 SM 的 B200 上一次跑 148 份，都对，只是快慢不同。PG 原话是 CUDA 能让"任意大的 grid 在任意大小的 GPU 上运行"。

那 block 之间要交换数据怎么办？ 三条路，后面章节会讲：

办法 怎么做 章节
拆成两个 kernel 第一个 kernel 写结果到显存，第二个 kernel 再读；kernel 之间天然有先后 第 10 章归约
原子操作 每个 block 把部分结果 atomicAdd 到同一个地址，不需要等对方 第 11 章
thread block cluster Hopper 起可以把相邻几个 block 绑成一组，保证同时在一个 GPC 里运行，组内可以同步、访问对方的 shared memory（PG §1.2.2.1.1） 第 17 章

第三步：一波一波地执行——wave 与尾部浪费（2026-11-14）

假设一个 SM 同时能放 2 个 block（能放几个由资源决定，第 8 章细讲），GPU 有 4 个 SM，于是一次最多同时跑 4 × 2 = 8 个 block。这"一次能同时跑的量"叫一个 wave（波）。

grid 有 20 个 block 时：

\[\text{波数} = \left\lceil \frac{20}{8} \right\rceil = 3\]

前两波各跑 8 个，第三波只有 4 个：这时一半的车间是空的。如果每个 block 耗时一样，总时间是 3 个 block 时长，但硬件利用率只有

\[\frac{20}{3 \times 8} = 83\%\]

这就是 tail effect（尾部效应）：最后一波不满，那段时间 GPU 有一部分在闲着。

数字演示（H100）：132 个 SM，每个 SM 放 1 个大 block（GEMM kernel 很常见）。

grid 大小 波数 最后一波占满多少 SM 利用率
132 1 132 / 132 100%
133 2 1 / 132 133 / 264 ≈ 50%
264 2 132 / 132 100%

多一个 block，耗时几乎翻倍。这就是为什么矩阵乘法 kernel 很在意 tile 大小和 SM 数的配合，后面会看到 persistent kernel、Stream-K 这类专门对付尾部效应的办法（第 18 章）。

反过来，block 太少也不行：grid 只有 50 个 block，132 个 SM 里 82 个从头到尾都闲着。经验规则是 block 数至少要是 SM 数的几倍，让每个 SM 都有活干，尾部占比也变小。

第四步：SM 内部——block 再拆成 warp（2026-11-14）

PG §3.2.2.2：SM 收到 block 后，把它按 32 个线程一组切成 warp，线程号 0–31 是第 0 个 warp，32–63 是第 1 个……切法永远固定。warp 数 = \(\lceil T / 32 \rceil\)（T 是 block 的线程数）。

每个 warp 的寄存器、程序计数器都一直留在 SM 片上，所以 SM 在不同 warp 之间切换不花任何代价：每个时钟周期，warp 调度器挑一个"下一条指令已经准备好"的 warp 发射出去。一个 warp 在等显存数据时，就换另一个 warp 来算——这是 GPU 隐藏延迟的核心手段，第 8 章细讲。warp 内部怎么执行是下一章的内容。

怎么看：

  1. 左边是排队的 block（工单），右边是 4 个 SM（车间），每个车间有 1 或 2 个槽位；

数学原理

  • 波数：每 SM 放 \(b\) 个 block、共 \(S\) 个 SM，grid 有 \(G\) 个 block，则波数 \(W = \lceil G / (bS) \rceil\)；每个 block 耗时相同时，利用率 \(= G / (W \cdot bS)\)。\(G\) 是 \(bS\) 的整数倍时利用率 100%；\(G = kbS + 1\) 时最差。
  • 为什么 block 多了尾巴就小：最后一波最多浪费 \(bS - 1\) 个槽位，占总槽位 \(W \cdot bS\) 的比例随 \(W\) 增大而变小，约为 \(1/W\) 量级。

关键几行：

per_wave = sms * per_sm                    # 一波能同时跑几个 block
waves = math.ceil(grid / per_wave)
last = grid - (waves - 1) * per_wave        # 最后一波有几个
util = grid / (waves * per_wave)            # 尾部效应下的利用率
order = rng.permutation(batch)              # 同一波里谁先做完是随机的

代码里才看得到的 2 件事：

  1. 结果和顺序无关，是因为 block 只写自己那一格：run_blocks 里 block b 只写 out[b]、只读自己那一段数据。要是某个 block 去读别人的 out，换个 seed 结果就会变——这正是第二步说的"block 之间不许等"。
  2. wave_stats 假设每个 block 耗时一样：真实 GPU 上 block 耗时有快有慢，调度器会把新 block 派给先空出来的 SM，所以"波"的边界没有这么整齐；但"最后一段时间有 SM 闲着"这件事不变。
