讲解

第一步：从"每个线程"到"每个 block"（2026-11-14）

回头看前面写过的东西：线程编号（第 1 章）、合并访存的映射（第 6 章）、shared memory 分块和 bank（第 7、13 章）、寄存器分块（第 14 章）、Tensor Core 片段布局（第 15 章）、异步拷贝和流水线（第 16–18 章）……这些都是"把一块数据的运算，手工分配给 block 里的每个线程"。

PG §1.2.2.3 给出另一种写法——Tile 编程模型：

程序员按整个 block 的视角写代码，描述对多维数据块（tile）的运算；编译器把这些运算映射到 block 的各个线程上。

PG 图 8 的对比：SIMT 里程序员写每个线程的代码、控制每个线程怎么访问数据；Tile 里程序员写每个 block 的代码，block 里有几个线程都由编译器决定。

几条规定（PG §1.2.2.3–1.2.2.3.1）：

  • block 里只有一条控制流，所以没有 warp 分岔的概念；标量运算（算下标、循环边界）由一个线程做，tile 运算由全体线程一起做；
  • tile 是不可变的值，每次运算产生新 tile；编译器决定它放在寄存器、shared memory 还是别处；
  • tile 每一维必须是 2 的幂、编译期已知；
  • 数据靠 load / store 在全局数组和 tile 之间移动，用 tile space（把数组切成等大的 tile，用 tile 坐标 (i, j) 索引）——越界部分自动处理。

第二步：同一个向量加法，两种写法（2026-11-14）

SIMT（第 1 章）：

__global__ void vecAdd(float* a, float* b, float* c, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) c[i] = a[i] + b[i];
}

Tile（cuTile Python，PG §2.4 的写法）：

import cuda.tile as ct

@ct.kernel
def vec_add(a, b, c, TILE: ct.Constant[int]):
    bid = ct.bid(0)                         # 这个 block 负责第几个 tile
    ta = ct.load(a, index=(bid,), shape=(TILE,))
    tb = ct.load(b, index=(bid,), shape=(TILE,))
    ct.store(c, index=(bid,), tile=ta + tb)

没有 threadIdx、没有 if (i < n)（越界由 tile space 的边界处理负责）、没有 __shared__、没有 __syncthreads()。C++ 版是 __tile_global__（PG §2.4.1）；矩阵乘是 tile 原语 ct.mma / mma（PG §2.4.9.1），编译器替你选 mma.sync / wgmma / tcgen05 和 TMA。

同一份 Tile 代码跨架构可移植——这是 NVIDIA 推它的主要理由（CUDA 13.1 起 Python、13.3 起 C++，02 生态 §2）。Rust 的 cutile-rs 是同一个 Tile IR 的第三个前端。

第三步：2026 年的 DSL 地图（2026-11-14）

04 调研 §3.2 的整理，按抽象层级从低到高：

层级 工具 你要管什么 编译器管什么 典型用户
线程 CUDA C++ / PTX 一切 寄存器分配、指令调度 学原理、榨最后 10%
tile + 线程 CuTe DSL（Python） layout、TMA / MMA atom、流水线、warp 分工 编译、部分调度 FA4、Quack
tile + 线程 ThunderKittens（C++） 16 × 16 寄存器 tile 原语、warp 分工 — HazyResearch 的 kernel
tile（可下到线程） TileLang（Python，TVM 后端） tile 划分、流水线级数、可选的线程级细节 布局、指令选择 DeepSeek TileKernels
tile cuTile（Python / C++ / Rust） tile 形状、block 负责哪块 线程映射、shared、异步、Tensor Core 官方路线
block Triton（Python） block 划分、tl.load / tl.dot 线程映射、shared、流水线、Tensor Core Liger、Unsloth、PyTorch Inductor
更高 Helion（Python，编译到 Triton） PyTorch 风格的写法 tile 大小等大量参数自动搜索 快速写融合算子

几点观察：

  • Triton 是生态最大的：PyTorch 的 torch.compile 默认生成 Triton；CS336 a2 用 Triton 写 FlashAttention（study-plan 阶段 9）。
  • 越往上写得越快、可移植性越好，但能控制的越少。FA4 选 CuTe DSL 而不是 Triton，就是因为要精确控制 TMEM、2-CTA、warp 分工（第 20、22 章）。
  • 作者自报的性能对比要谨慎看：Helion 团队报告平均比 torch.compile 快 1.21 倍、比手写 Triton 快 1.85 倍，但 Red Hat 的跨厂商基准里它在某张消费卡上异常慢（04 调研 §3.2）。

第四步：怎么选（2026-11-14）

04 调研 的选型口诀：先 Triton 写对，性能不够上 CuTe DSL / TileLang，要懂原理写 C++。 展开一点：

  1. 逐元素 / 归约 / norm 等融合算子，没有特殊硬件需求 → Triton（或 Helion、torch.compile 自动生成）；
  2. 想跨 NVIDIA 架构可移植、又要用 Tensor Core 的稠密计算 → cuTile；
  3. 要支持国产卡或多后端 → TileLang；
  4. 要在 Hopper / Blackwell 上做到接近峰值、需要控制 TMA / TMEM / warp 专业化 → CuTe DSL 或 CUTLASS C++；
  5. 学习、调试、读别人的 kernel → CUDA C++ / PTX（这本书的前 22 章）。

为什么还要学 SIMT？ 因为 DSL 生成的 kernel 慢了、错了，你得能读懂 Nsight 报告和 PTX / SASS，知道是合并访存、bank conflict、occupancy 还是流水线出了问题——这些概念在哪一层 DSL 里都一样。

怎么看：

  1. 同一个 16 × 16 的矩阵加法，切成 4 个 8 × 8 的 tile，分给 4 个 block；
  2. SIMT 模式：放大一个 block，里面 64 个线程各自算下标、各取一个元素，旁边列出程序员要写的东西（下标、越界检查、同步）；
  3. Tile 模式：block 整块 load、整块相加、整块 store，旁边列出的变成"编译器替你做"；
  4. 最后一帧并排对比两边的代码行数。

数学原理

  • tile space：形状 \((M, N)\) 的数组按 \((t_m, t_n)\) 切，tile 坐标 \((i, j)\) 覆盖元素 \([it_m, (i+1)t_m) \times [jt_n, (j+1)t_n)\)；tile 数 \(\lceil M/t_m \rceil \times \lceil N/t_n \rceil\)（PG §1.2.2.3.2）。
  • 这和第 19 章 CuTe 的 zipped_divide 是同一个概念：Tile 模型把它做成了语言内置。

关键几行：

for bid in range(-(-len(a) // tile)):     # ct.bid(0)：这个 block 负责第几块
    ta = tile_load(a, bid, tile)           # ct.load：越界部分补 0
    tb = tile_load(b, bid, tile)
    tile_store(c, bid, ta + tb)            # ct.store：只写回数组里存在的部分

代码里才看得到的 3 件事：

  1. -(-n // tile) 是向上取整的另一种写法：Python 的 // 向下取整，对负数取两次负号就变成向上取整；和第 1 章的 (n + B - 1) // B 结果一样。
  2. ta + tb 产生新数组：对应讲义说的"tile 是不可变的值，每次运算产生新 tile"。
  3. Tile 写法里的"block 里几个线程"根本没出现：这正是 Tile 模型的意思——由编译器决定。
